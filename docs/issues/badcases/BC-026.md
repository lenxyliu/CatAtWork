# BC-026 — Current 30 Hz animation clock quantizes authored cadence

- Status: open
- Classification: current-confirmed
- ISSUE: ISSUE-023; GitHub #18
- First observed: 2026-07-24
- Affected versions: app 1.0.3 (8), commit `0ca2b518d5a079ace1ef1e6d9a6892a5259b080e`
- Fixed versions: none
- Regression test: B1 cadence probe; no product gate yet
- Automated evidence: QA root `Assets/CatAtWork/qa/b1-current-build-0ca2b518`; scope digest `ae55f2d9ed0bfadf9314cc4146ee62523686c3b2878e3ec57bd6995b4e27a938`
- Device evidence: active display modes included 60 Hz and 120 Hz

## Preconditions

Use the current controller ordering: animation advances only on the 30 Hz
watchdog; display-cadence physics/render samples occur at 60 or 120 Hz.

## Reproduction

Compile and run `runtime-probe.swift`, sampling representative 12 fps
(`idleEar`), 14 fps (`walkRight`) and 18 fps (`runRight`) actions at 60 and
120 Hz.

## Expected

Each authored frame stays within one display period of its declared duration
without a periodic long/short quantization pattern.

## Actual

At both refresh rates, 12 and 14 fps frames quantize to approximately
**66.667/100 ms** holds. Eighteen fps frames quantize to approximately
**33.333/66.667 ms**. Maximum errors from declared duration are **16.667
ms**, **28.571 ms** and **22.223 ms**, respectively.

## Root cause

Confirmed current clock ownership: `Timer(1/30)` advances the animation player,
while display link callbacks only step physics and redraw.

## Impact

Authored cadence is visibly uneven and can diverge from smoother world motion,
especially on a 120 Hz display.
